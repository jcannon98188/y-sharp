# Hostile input is attacked by nine named classes, three generator layers and tiered runs

Extends ADR 0005 (outcomes), 0009 (allocation bound), 0010 (tags), 0011 (stored negative cases) and 0012 (differential). ADR 0005 says what must happen to hostile bytes; this says how the suite proves it.

- **Classes.** Nine, each with a stable ID used in `[Covers]` tags and corpus headers. Expected outcomes, all subject to the post-condition below:
  - `HOS-TRUNC`: truncation at every byte offset of every valid fixture (updates V1/V2, state vectors, sync and awareness frames). A cut strictly inside the structure gives `Malformed` and changes nothing.
  - `HOS-MUT`: bit flips, byte overwrites, insertions, deletions and splices of valid bytes. Any result is allowed except crash, hang, faulted document or over-allocation.
  - `HOS-LEN`: oversized counts and lengths (clients, structs, strings, arrays, buffers, V2 columns), up to 2^53 and the ten-byte overflow forms. `LimitExceeded` or `Malformed`, with allocation within the ADR 0009 bound.
  - `HOS-DEEP`: Any values 100k deep, and documents with 1M nested types. Any depth gives a `MaxAnyDepth` rejection; document depth is never recursed on in apply, delete, GC, traversal or encode.
  - `HOS-CLOCK`: gaps, a first clock above 0, overlaps, duplicate clients (last wins), clocks near 2^31 and 2^53, `clock+length` overflow, zero-length structs, client ids at or above 2^31.
  - `HOS-REF`: missing, self-referencing, cyclic (A to B to A across clients), GC/Skip-targeting or non-type parents. Unresolvable references become pending, bounded by `MaxPendingBytes`, or rejected structs; the resolver never spins.
  - `HOS-SEM`: well-formed but meaningless input: unknown content refs, invalid UTF-8, lone surrogates, unsorted or overlapping delete sets, deletes over unknown clients.
  - `HOS-AMP`: amplification: millions of 1-byte structs, a delete range claiming 2^40 clocks, thousands of tiny pending updates, quadratic merge or diff shapes.
  - `HOS-PROTO`: unknown sync/awareness message types, length overruns, concatenated frames, non-JSON awareness state, clock regression.
- **Post-condition.** After every hostile input the document must not be faulted, `encodeStateAsUpdate` must work, and a known-good update must still apply. This is what proves "a failed apply leaves a consistent document".
- **Corpus.** `fixtures/hostile/` holds a hand-written fixed corpus (the ADR 0011 negative cases plus the "OK for hostile input" rows of `encoding.md`), seeds from the Node generator and the simulation op logs, and byte-level mutations of those seeds. Files carry the usual pinned-version header plus `class`, `seed`, discovery date and the oracle outcome when known. A coverage-guided fuzzer (SharpFuzz with AFL++ or libFuzzer) runs as a documented, non-gating nightly job; anything it finds is minimised and committed to the fixed corpus.
- **Generators.** Three FsCheck layers: a raw-byte mutator over valid seeds; a structure-aware update builder in the test project that writes V1/V2 from a struct and delete-set model without using y-sharp's encoder (so it reaches pending/reject logic and independently checks the decoder); and the ADR 0012 ops-script generator with delivery-schedule mutation (reorder, drop, duplicate). Shrinking goes to the shortest bytes, then the fewest structs. A failure writes a corpus candidate file.
- **Guards.** Each input runs on a worker thread with a per-input timeout (start 2 s); a timeout is a y-sharp hang. Allocation is bounded by k·N plus a constant (start k=64, 1 MB), calibrated from the corpus and ratcheted down. Decode and apply run on a probe thread with a small stack (256 KB) so recursion on input depth fails fast. A small out-of-process canary host runs only `HOS-DEEP` document-depth cases, so a stack overflow is reported as a named test failure instead of killing the run. The fuzz process runs under a `GCHeapHardLimit` of a few hundred MB.
- **Tiers.**
  - Per-commit, gating, about 2 minutes, no Node: the fixed corpus, truncation sweeps (the oracle outcome table is stored per ADR 0011), the canary, and FsCheck with fixed seeds (about 500 cases per layer).
  - PR smoke, non-gating at first: hostile cases of the ADR 0012 differential, fixed seeds, about 1 minute.
  - Nightly, about 20 to 30 minutes: random-seed FsCheck with a time box (about 100k cases per layer), the differential mutation comparison, 1M-struct amplification, the SharpFuzz job, and a pass under tiny limits.
  - Anything that needs Node or runs over about 10 seconds is not in the gating tier. A failing nightly seed is a real bug: never retried, never quarantined (ADR 0006).
- **Oracle comparison.** Only in the smoke and nightly tiers. Per input the outcome class is compared: JS accepts or rejects against y-sharp accepts or rejects. JS accepts and y-sharp rejects needs a registered divergence ID, or the run fails (this is the dangerous direction: being stricter than real peers). Both accept means equal final state. JS crashing (stack overflow, `unexpectedCase`) with y-sharp rejecting is counted, not compared. The per-commit tier asserts y-sharp's contract only, using stored oracle outcomes.
- **Limits in tests.** Boundary tests for `HOS-LEN`, `HOS-DEEP` and `HOS-AMP` run under both the defaults and a tiny `YLimits` (for example `MaxAnyDepth=8`, `MaxStructsPerUpdate=100`, `MaxPendingBytes=1 KB`): exactly at the limit is accepted, one over is rejected. A separate test shows the defaults reject nothing in the valid fixture and simulation corpora and fall in a sane numeric range. Fuzz runs under the defaults, plus a nightly pass under the tiny limits to exercise limit-triggered paths mid-update.
- **Regression.** A found failure is committed as one minimised file in `fixtures/hostile/` with its header and `HOS-*` tag. The gating suite replays every file in the folder, so adding the file is the whole regression test. There is no separate log; the folder's git history is the log.
