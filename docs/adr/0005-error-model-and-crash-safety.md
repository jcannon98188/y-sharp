# Typed, non-throwing error model with contained failures

Hostile bytes are expected input, so y-sharp reports them as data and never lets them crash, hang, over-allocate or corrupt a document. This departs from Yjs in several recorded places; each departure has a tagged test that shows the JS behaviour (ADR 0003).

- **Two entry points.** `TryApplyUpdate` (and the sync and awareness readers) return a `readonly struct ApplyResult` with a status, an error code (`Malformed`, `LimitExceeded`, `Rejected`, ...), a rejected-struct count and an observer-fault count. The throwing `ApplyUpdate` wraps it with a `YDecodeException`. JS error classes and messages are collapsed into codes and never compared.
- **Strict decoding.** EOF is always a decode error (JS yields 0 for a varint at EOF and for exhausted V2 columns). Trailing bytes, duplicate clients (last wins) and unsorted input stay accepted.
- **Atomic decode, quarantined integration.** The whole update, structs and delete set, is decoded and validated before anything is integrated; a decode failure changes nothing (JS integrates structs before reading a truncated delete set). Pending structs are retained state, not failure. A well-formed struct that cannot be integrated (for example its parent is not a type) is rejected with its dependents, never retried, and the rest applies; the document stays structurally consistent.
- **Limits.** A `YLimits` options object with safe defaults (`MaxUpdateBytes`, `MaxAnyDepth`, `MaxStructsPerUpdate`, `MaxPendingBytes`, `MaxStringBytes`). No allocation is sized from a length claim until it is checked against the bytes remaining. At `MaxPendingBytes` a new update is rejected and the existing pending state is kept.
  - *Semantics (decided).* A limit is exceeded when the value is greater than the limit: a value equal to the limit is accepted, one more is `LimitExceeded`. The check runs on the length claim, before anything is allocated or read for it. It applies on every decode path: `TryApplyUpdate`, `YUpdate.TryMerge`, `TryDiff`, `TryConvert`, `TryStateVectorFromUpdate` and `TryValidate` (each takes an optional `YLimits`, default `YLimits.Default`), for V1 and for every V2 column. A `LimitExceeded` result leaves the document unchanged, as a `Malformed` one does.
  - *What is measured.* `MaxUpdateBytes`: the length of one input update buffer, trailing bytes included (each update of a merge is checked on its own). `MaxStructsPerUpdate`: every struct of the update, GC and Skip included, over all clients. `MaxStringBytes`: the claimed UTF-8 length of one string. `MaxAnyDepth`: nested containers (an array holding an array is depth 2; a scalar leaf adds none). `MaxPendingBytes`: the V1 encoding of the pending state retained after the update, so an update that would take it above the limit is rejected whole.
- **No recursion on document depth.** Every internal traversal is iterative; document nesting has no cap. Only decoded Any depth is capped. JS overflows its stack here.
- **Observer faults are contained.** All handlers run, cleanup completes, the data is committed and `update` is emitted, as in JS, but exceptions never unwind through `ApplyUpdate`, `Transact` or local mutations; they are reported through an `ObserverFaulted` event and the result. Exceptions from the caller's own `Transact` body propagate. JS rethrows the first error.
- **Local API.** Programmer errors use a separate exception family from `YDecodeException`. JS-defined behaviour is replicated (array overflow throws, text clamps); undefined cases such as negative indexes throw `ArgumentOutOfRangeException` and are excluded from the differential.
  - *Lifetime misuse (decided).* Using a pooled or live view after the transaction or dispatch that produced it ended (a `Transaction` kept past its body, a `YEvent` kept past dispatch, a change collection or an enumerator taken inside an explicit transaction) throws one type, `YLifetimeException : YException`, and never returns old contents. `IsValid` is the only member that stays callable. Existing types do not fit: `YConcurrencyException` is for lock-protocol misuse (read-to-write upgrade, lock order) and the stale view is a single-threaded error too; `InvalidOperationException` and `ObjectDisposedException` sit outside the `YException` family that ADR 0005 reserves for programmer errors, and nothing is being disposed (the objects are pooled). An enumerator taken outside an explicit transaction snapshots and is never stale.
- **Environment and internal faults.** `OutOfMemoryException` and similar are never caught. A violated internal invariant throws `YInternalException` and marks the document faulted: readable, but it rejects further mutation and apply. The fuzz suite asserts that no input ever faults a document.
  - *Faulted documents (decided).* On a faulted document `IsFaulted` is true; reads and `EncodeStateAsUpdate` work; local mutators and `ApplyUpdate` throw `YInternalException`; `TryApplyUpdate` returns `Rejected` and changes nothing. The fault is permanent: there is no API to clear it. A caller recovers by applying `EncodeStateAsUpdate` from the faulted document to a fresh `Doc` (confirmed by the owner, TASK-3.1). *Fault hook.* The invariant violation is tested through `internal void Doc.InjectInvariantViolation()`, visible to the test assemblies through `InternalsVisibleTo` (ADR 0015). It breaks a struct-store invariant without any public call; the next operation that touches the store detects it, throws and faults the document (ERR-20). It is not public API and is not callable from the interop project.
  - *Out-of-memory (ERR-19, confirmed).* An `OutOfMemoryException` thrown by an observer propagates out of the call that triggered it. It is not an observer fault, is not passed to `ObserverFaulted`, and the document is not marked faulted.
