# Ops scripts address replicas by name, group edits in `transact` steps, and compare typed dumps

Fills in ADR 0011 (fixtures), 0012 (differential) and 0013 (fuzz op logs). Both interpreters, the FsCheck generators and every area spec use this one vocabulary. Schema version stays `schema: 1` until a breaking change.

- **Addressing.** A script declares named replicas (`a`, `b`, ...) with explicit `clientId` (and `gc` flag). A step names its replica in `doc`. A shared type is addressed by `{root: "name", kind: "text|array|map|xmlFragment"}` or by a path of keys and indices from a root (`[{root:"t",kind:"map"}, "k", 2]`) for nested types. Paths resolve at replay time on both sides; scripts never carry handle ids. A path that does not resolve is a script error, not a y-sharp failure.
- **Transactions.** `transact {doc, origin?, steps:[...]}` wraps child steps in one transaction. A bare mutating step is its own implicit transaction (ADR 0008). Nested `transact` is allowed and joins the outer one, so re-entrancy is scriptable. Observer registration is a step (`observe {doc, target, name}`); fired events are recorded under the `events` observation in firing order, keyed by the observer name.
- **Determinism.** Scripts supply every value that could differ between runs: `clientId`, subdoc `guid`, PermanentUserData device and user ids, and time through `tick {ms}` on the virtual clock. An interpreter refuses a script that omits one; it never invents a default.
- **Step kinds.**
  - *Replicas and delivery:* `replica`, `sync {from,to}`, `applyUpdate {doc,bytes,encoding}`, `applyForeign` (ADR 0012), `mergeUpdates`, `diffUpdate`, `convertUpdate`, `deliver {schedule}` (order, duplicate, drop).
  - *Y.Text:* `text.insert {at,value,attributes?}`, `text.insertEmbed`, `text.delete {at,len}`, `text.format {at,len,attributes}`, `text.applyDelta`.
  - *Y.Array:* `array.insert`, `array.push`, `array.unshift`, `array.delete` (v13 has no move).
  - *Y.Map:* `map.set`, `map.delete`, `map.clear`.
  - *XML:* `xml.insert`, `xml.delete`, `xml.setAttribute`, `xml.removeAttribute`, plus `text.*` on XmlText.
  - *Nested types:* `*.insertType {kind, init?}` so the new type is reached later by path.
  - *Values:* any argument that is an Any value uses the ADR 0011 tagged values.
  - *Doc features:* `gc.run`, `subdoc.add/load/destroy {guid, opts}`, `snapshot.take {name}`, `snapshot.restore`, `relpos.create {name, at, assoc}`, `relpos.resolve`, `undo.create {name, scope, captureTimeout, trackedOrigins}`, `undo.stopCapturing`, `undo.undo`, `undo.redo`, `pud.setUserDescription`, `pud.observe`.
  - *Protocol:* `sync.step1`, `sync.step2`, `sync.update`, `awareness.setLocal {state}`, `awareness.applyUpdate {bytes}`, `awareness.removeStates`, `awareness.encode`.
  - *Time:* `tick {ms}`.
  - An area registers its step kinds and observations with the interpreters without changing the core (ADR 0012); the exact field list of each kind lives in the schema file `tools/fixture-gen/schema/ops.schema.json`, which is the normative vocabulary.
- **`doc` dump.** A typed tree of every root, in sorted root-name order. `{kind:"text", delta:[{insert, attributes?}...]}` (embeds as tagged values, adjacent equal-attribute runs merged); `{kind:"array", items:[...]}`; `{kind:"map", pairs:[[key, value]...]}` in the order the oracle's iteration yields (the JS integer-key rule is tested, not assumed); `{kind:"xmlFragment|xmlElement|xmlText", name?, attrs:[[k,v]...], children:[...]}`; nested types appear in place. Scalars use the tagged values, so `-0`, `NaN`, lone surrogates and BigInt are distinguished.
- **`structs` dump (opt-in).** For each client in descending client-id order, a clock-ordered list of `{id:[client,clock], len, kind:"item|gc|skip", origin?, rightOrigin?, parent, parentSub?, content:{ref, value}, deleted, keep}`; `gc` and `skip` entries carry only id and length. `parent` is a root name or an id. Two dumps are compared structurally and the first difference is reported as a path (ADR 0012). The delete set is the `ds` observation as sorted `[client, [[clock,len]...]]`.
- **Truncation outcomes.** Beside each valid fixture, a run-length list `{from, to, outcome}` over cut offsets `from..to`, with `outcome` one of `ok` (decodes and applies), `throws`, or `lenient-accepts` (the oracle accepts a shorter prefix; the entry adds the `doc` dump hash after applying). y-sharp must fail atomically for every cut strictly inside the structure whatever the oracle did; the list drives divergence classification (ADR 0010 exclusions, ADR 0013 `HOS-TRUNC`), and an oracle `lenient-accepts` on such a cut needs a registered divergence ID.
- **Validation.** The schema file validates every fixture and every generated script in both languages; the C# loader rejects unknown step kinds and unknown fields. Adding a step kind needs a schema change, an interpreter on each side, and a `[Covers]` entry.
