# Allocation and memory are gated by exact counters, not by time

Pure C# (ADR 0004) makes GC pressure the main engineering risk, so it is proven by assertions rather than hoped for. Wall-clock time is never asserted because shared CI runners make it flaky.

- **Hot paths.** Eleven named paths carry allocation assertions. Zero bytes: contended `TryTransact`, scalar `YValue` reads and `AttributeEquals`, `EncodeStateAsUpdate` into a pre-sized writer. Bounded: uncontended `Transact`/`ReadTransact` with a static lambda and uncontended `TryTransact` (one small `Transaction` per transaction, so a kept one stays stale; owner decision, TASK-4.12), event dispatch with no handlers, a commit with no `Update` subscriber and a one-character `YText.Insert` at the end (each insert allocates an `Item` and each transaction its `Transaction`, so zero is out of reach; TASK-4.27, owner sign-off 2026-10-26; TASK-8 tried for zero and tightened the limits), `TryApplyUpdate` (V1, V2), `Push`/`Set` of scalars, a sync Step1/Step2 round trip, awareness encode and apply.
- **Measurement.** A plain xUnit helper around `GC.GetAllocatedBytesForCurrentThread`, Release only, with `TieredCompilation` off so escape analysis and stack allocation behave the same on every run. A failed budget reruns under an `EventListener` to name the allocating types. BenchmarkDotNet never gates.
- **Budget values.** Zero paths stay at 0. Bounded budgets are measured on the first implementation, set at that value plus 25% headroom, and only move down; raising one is a reviewed change with a reason. Budgets live in one `AllocationBudgets` table with stable IDs that tests reference and a script cross-checks.
- **Hostile input.** For an input of N bytes, allocation stays at or below k·N plus a fixed amount, asserted on every fuzz input and on the fixed hostile corpus. A violation is a crash-safety bug (ADR 0005).
- **Memory.** A slow tier measures retained managed heap per operation after a forced collection on three large workloads (1M text inserts, 1M array pushes, 100k map keys). "Bytes per item" means retained bytes divided by workload operations, not by structs, as `bench/yjs-memory/measure.mjs` computes it. Structs per operation is reported beside it but not gated (TASK-3.5). Bytes per operation must not exceed the figure Yjs produced on the same workload, recorded in the fixture header. Half of Yjs's figure is a goal, not an assertion. The same tier requires zero gen2 collections and no large-object-heap growth (beyond a declared one-off allowance) during 100k steady-state edits (the mix is `MemoryWorkloads.SteadyStateEdits`: alternating one-character inserts and deletes within 15 characters of the end of a 10,000-character text, one implicit transaction each, after 2,000 warm-up edits), so the implementation needs chunked storage. Pause time is report-only.
- **Benchmark-only.** Throughput, merge and diff, building a 1M-item doc, the y-sharp-versus-Yjs table, lock cost, and the bytes-per-item table. A nightly job compares results against the last stored run and flags regressions without failing the build.
